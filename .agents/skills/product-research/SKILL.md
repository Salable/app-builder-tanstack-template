# Research that changes the plan

Start with the accepted brief, displayed planning stage and actual repository
stack. Identify the decisions research can improve. Preserve accepted choices;
an evidence-backed alternative is a recommendation, never a scope change or an
approval. Explicit monetisation opt-out remains authoritative.

Read only the relevant research branch:

- Competitors, positioning or pricing: [market and pricing](references/market-and-pricing.md).
- Libraries, APIs, requested features or complex workflows:
  [implementation research](references/implementation-research.md).

Consider performance, efficient data access, accessibility, privacy and applicable
SEO as normal engineering responsibilities. Recommend proportionate baselines
without a technical questionnaire. Ask only for a material product choice that
the available brief and context cannot settle.

For each consequential recommendation, retain the decision, supporting sources,
date/version context, applicability, uncertainty and resulting implementation or
test requirement. Distinguish a documented provider capability from a locally
tested integration and from observed hosted behaviour. Do not substitute an
agent's preference or a simulated persona for user research.

Prefer primary sources: official product pricing, documentation, API schemas,
release notes, maintained repository source and original research. Fetch the
referenced page, not just its search snippet. Verify technical examples against
the selected versions. If sources disagree, preserve the disagreement and its
effect on the plan; do not invent an API or choose the convenient claim silently.

Work within the current research operation's result schema and source limits.
Do not invent sources to fill a quota, rewrite workflow rules or advance a stage.
Present findings and optional alternatives for direction; research completion
does not itself authorize specification, catalog creation or implementation.
